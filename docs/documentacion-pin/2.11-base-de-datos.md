# 2.11 — Base de Datos

> Requisito oficial: Modelo de datos · Diccionario de datos · Scripts principales (opcional)

## Modelo de datos

Motor: **PostgreSQL** (gestionado por Supabase). El esquema no vive en archivos `.sql`
sueltos — se define programáticamente en `backend/db/database.js` mediante
`CREATE TABLE IF NOT EXISTS`, que se ejecuta al iniciar el servidor. Ver el diagrama
Entidad-Relación completo en el apartado 2.7.

13 tablas: `users`, `pets`, `pet_carnets`, `lost_pets`, `posts`, `post_likes`, `post_comments`,
`stories`, `favorites`, `carnets`, `chats`, `messages`, `notifications`.

## Diccionario de datos

### `users`
| Campo | Tipo | Descripción |
|---|---|---|
| id | SERIAL PK | Identificador único |
| name | TEXT | Nombre del usuario |
| email | TEXT UNIQUE | Email, usado para login |
| password_hash | TEXT | Contraseña hasheada con bcrypt |
| city | TEXT | Ciudad del usuario (base actual para filtros/alertas) |
| avatar_url | TEXT | Foto de perfil |
| created_at | TIMESTAMP | Fecha de alta |

### `pets`
| Campo | Tipo | Descripción |
|---|---|---|
| id | SERIAL PK | Identificador único |
| name, species, breed, age, size | TEXT | Ficha de la mascota |
| location | TEXT | Ubicación (texto libre, usada en filtros del catálogo) |
| image_url | TEXT | Foto |
| badge, badge_color | TEXT | Etiqueta visual (ej. "Nuevo") |
| description | TEXT | Descripción |
| is_adopted | INTEGER | 0/1 — si ya fue adoptada |
| adopted_quote | TEXT | Frase de cierre cuando se adopta |
| health_status | TEXT | Cartel de estado de salud del catálogo: `disponible`, `con_cuidado`, `en_reposo` o `cirugia_programada` (CHECK en la base) |
| health_note | TEXT | Aclaración del estado (ej. "reposo hasta el 2/10"); se vacía al volver a `disponible` |
| user_id | INTEGER FK → users.id | Dueño que publicó |
| created_at | TIMESTAMP | Fecha de publicación |

### `pet_carnets`
Carnet digital de cada animal del catálogo (RF-26). Relación 1 a 1 con `pets`
(`pet_id UNIQUE`, borrado en cascada). Es distinta de `carnets`, que es el carnet
de la mascota propia de un usuario.

| Campo | Tipo | Descripción |
|---|---|---|
| id | SERIAL PK | Identificador único |
| pet_id | INTEGER FK → pets.id, UNIQUE | Mascota del catálogo |
| gender, birth_date, color_markings, microchip_id | TEXT | Identificación |
| weight_kg | NUMERIC | Peso |
| spayed_neutered | INTEGER | 0/1 — esterilizado |
| vaccinations | TEXT (JSON) | Lista de `{name, last_dose, next_dose, status}`; `status` ∈ `updated`, `expiring`, `expired` |
| diseases | TEXT (JSON) | Lista de `{name, status, notes}`; `status` ∈ `activa`, `en_tratamiento`, `cronica`, `curada` |
| treatments, allergies | TEXT | Tratamiento en curso y alergias |
| medical_history | TEXT (JSON) | Lista de `{date, title, description}` |
| vet_name, vet_clinic, vet_phone | TEXT | Veterinario de referencia |
| updated_at | TIMESTAMP | Última modificación |

### `shelter_suggestions`
Refugios aportados por la comunidad para el mapa de la página *Refugios*. Los refugios
chicos (de pueblo, de una casa, de un perfil de Instagram) no figuran en ninguna base de
mapas, así que los carga quien los conoce y un admin los revisa antes de publicarlos.
Se guarda un link de verificación y **no un teléfono**: muchos son casas particulares.

| Campo | Tipo | Descripción |
|---|---|---|
| id | SERIAL PK | Identificador único |
| user_id | INTEGER FK → users.id | Quién lo sugirió |
| name | TEXT | Nombre del refugio (3 a 80 caracteres) |
| city | TEXT | Localidad |
| address | TEXT | Referencia opcional (barrio, "cerca de la plaza") |
| lat, lng | NUMERIC | Punto marcado en el mapa |
| approximate | INTEGER | 0/1 — si es 1, el mapa público muestra el punto redondeado a ~100 m |
| url | TEXT | Link de su perfil o web (http/https), para verificarlo |
| notes | TEXT | Observaciones opcionales (hasta 300 caracteres) |
| status | TEXT | `pendiente`, `aprobado` o `rechazado` (restricción CHECK en la base) |
| review_note | TEXT | Motivo que escribe el admin al rechazar |
| reviewed_by | INTEGER FK → users.id | Admin que lo revisó |
| reviewed_at, created_at | TIMESTAMP | Fechas de revisión y de alta |

### `lost_pets`
| Campo | Tipo | Descripción |
|---|---|---|
| id | SERIAL PK | Identificador único |
| name, breed, description | TEXT | Ficha de la mascota perdida |
| location | TEXT | Ubicación en texto |
| last_seen | TEXT | Última vez vista |
| image_url | TEXT | Foto |
| **marker_top, marker_left** | TEXT | ⚠️ Guardan latitud/longitud reales como texto, pero el nombre de columna es heredado de un diseño anterior (pin en % sobre imagen). Recomendado renombrar/tipar a `lat NUMERIC` / `lng NUMERIC` antes de construir alertas por radio de distancia. |
| is_found | INTEGER | 0/1 — si ya fue encontrada |
| user_id | INTEGER FK → users.id | Quién reportó |
| created_at | TIMESTAMP | Fecha del reporte |

### `posts`, `post_likes`, `post_comments`
Módulo de comunidad. `posts` tiene `title`, `body`, `category`, `tags` (JSON en texto) y
`user_id`. `post_likes` es una tabla puente con `UNIQUE(post_id, user_id)` para evitar
likes duplicados. `post_comments` guarda `body` + relación a `post_id` y `user_id`.

### `stories`
Historias de éxito: `pet_name`, `author_name`, `title`, `body`, `image_url`, `badge`,
`is_approved` (0/1 — permite moderación antes de publicar), `user_id`.

### `favorites`
Tabla puente `user_id` + `pet_id`, con `UNIQUE(user_id, pet_id)`.

### `carnets`
Carnet digital / pasaporte de mascota: datos de identificación (`pet_name`, `species`,
`breed`, `gender`, `color_markings`, `microchip_id`, `birth_date`), historial médico
(`vaccinations`, `medical_history` — ambos JSON en texto), datos del veterinario
(`vet_name`, `vet_clinic`, `vet_phone`, `vet_image`), datos del dueño (`owner_name`,
`owner_city`) y `qr_url` para compartir el carnet. Relacionado a `user_id`.

### `chats` y `messages`
`chats` vincula `pet_id`, `adopter_id` y `owner_id` — se crea automáticamente cuando un
usuario hace clic en "Adoptar". `messages` guarda cada mensaje (`chat_id`, `sender_id`,
`body`).

### `notifications`
`user_id`, `type` (ej. `adoption_request`, mensaje nuevo), `related_id`, `text`,
`is_read`. Hoy solo se generan notificaciones para solicitudes de adopción y mensajes de
chat — **no** para alertas de mascotas perdidas por cercanía (pendiente, ver 2.6/2.10).

## Scripts principales

No hay archivos `.sql` de migración — el esquema se crea en código
(`backend/db/database.js`, función `initDatabase()`), y la base se siembra
automáticamente con datos de ejemplo (`seedDatabase()`) la primera vez que arranca vacía,
incluyendo 3 cuentas demo (`demo@patamatch.com`, `david@patamatch.com`,
`sarah@patamatch.com`, contraseña `demo123`) — útiles para las capturas del manual de
usuario y para las pruebas.

## Instalación del sistema

Requisitos previos: Node.js instalado, una base PostgreSQL accesible (Supabase o local).

```bash
git clone https://github.com/benjamincarnero1213-cmyk/Patamatch.git
cd Patamatch
npm install
```

## Configuración

Crear un archivo `.env` en la raíz con:

```
DATABASE_URL=postgres://usuario:password@host:puerto/basededatos
JWT_SECRET=una-clave-secreta-larga-y-aleatoria
GEMINI_API_KEY=clave-de-google-ai-studio          # asistente de adopción (2.10)
GOOGLE_MAPS_API_KEY=clave-de-google-cloud          # opcional: mapa de refugios
PORT=3000
```

`GOOGLE_MAPS_API_KEY` habilita la búsqueda de refugios de la zona con **Google Places
(Text Search)** en la página *Refugios*. Se obtiene en Google Cloud Console activando la
API "Places API (New)". Es opcional, pero **es lo que da una cobertura completa**: busca
dentro del área visible del mapa con tres consultas ("refugio de animales", "protectora de
animales y rescate animal" y "animal shelter"), pagina hasta 60 resultados por consulta,
elimina duplicados y descarta lo que no es un refugio (casillas de montaña, tiendas,
veterinarias comunes y locales cerrados).

Si la clave no está definida, o Google responde con error (clave inválida, API sin
habilitar, cuota agotada), el sistema consulta **OpenStreetMap (Nominatim)** con la
categoría `animal_shelter`, sin clave. Esa fuente solo trae lo que alguien cargó en
OpenStreetMap, que en muchas ciudades de Latinoamérica es muy poco (por ejemplo, 1 refugio
en Córdoba, Argentina, y ninguno en Buenos Aires), por lo que la página avisa que la
lista puede estar incompleta.

La búsqueda de la zona siempre se hace desde el servidor
(`GET /api/refugios/externos?s=&w=&n=&e=`, con el recuadro visible del mapa) para no
exponer la clave, y se cachea 10 minutos por zona. Requiere un zoom mínimo de 10 (una
ciudad); con el mapa más alejado se pide acercarlo.

**Refugios aportados por la comunidad.** Ninguna de las dos fuentes anteriores conoce los
refugios chicos de pueblo, que viven en Instagram o Facebook. Para esos, cualquier usuario
con sesión puede usar el botón *Sumá un refugio* de la página *Refugios* (nombre,
localidad, punto en el mapa, link de su perfil y observaciones). Queda **pendiente** hasta
que un admin lo aprueba desde el panel de gestión; si quien lo carga es admin, se publica
directo. Al aprobar o rechazar se notifica a quien lo sugirió. Endpoints
(`backend/routes/refugios-comunidad.js`):

| Método y ruta | Acceso | Qué hace |
|---|---|---|
| `GET /api/refugios/comunidad` | Público | Los aprobados, para el mapa (sin datos internos; los puntos aproximados salen redondeados a ~100 m) |
| `POST /api/refugios/comunidad` | Sesión iniciada | Sugiere un refugio. Valida los campos, rechaza duplicados (mismo nombre a menos de ~200 m) y limita a 5 sugerencias pendientes por usuario |
| `GET /api/refugios/comunidad/moderacion?estado=` | Solo admin | Todas las sugerencias, las pendientes primero |
| `PUT /api/refugios/comunidad/:id` | Solo admin | Aprueba, rechaza (con motivo) o devuelve a pendiente |

Las claves nunca deben subirse al repositorio (`.env` ya está en
`.gitignore`). Al arrancar por primera vez con una base vacía, el sistema crea las
tablas automáticamente y las siembra con datos de ejemplo (ver 2.11).

**Levantar en local:**
```bash
npm run dev     # con recarga automática
npm start        # modo normal
```

Servidor disponible en `http://localhost:3000`. Cuentas de prueba ya sembradas:
`demo@patamatch.com` / `david@patamatch.com` / `sarah@patamatch.com`, contraseña
`demo123` para las tres.

**Despliegue en producción:** configurado para Vercel vía `vercel.json` — el backend se
despliega como función serverless y el frontend como sitio estático, con `/api/*`
enrutado al backend. Las variables de entorno se configuran en el panel de Vercel, no en
un archivo.

## Estructura del código

```
backend/
  server.js          → entrypoint, define middlewares y monta las rutas
  db/database.js      → conexión a PostgreSQL, esquema y datos semilla
  middleware/
    auth.js            → requireAuth / optionalAuth (verificación de JWT)
    sanitize.js         → sanitización contra XSS
  routes/
    auth.js, pets.js, lost-pets.js, posts.js, stories.js,
    favorites.js, carnets.js, chats.js, notifications.js
frontend/
  index.html
  js/api.js           → cliente HTTP centralizado hacia /api
  js/pages/            → un archivo JS por sección (adoptar, mascotas-perdidas,
                          comunidad, historias, carnet, chats, perfil, login, registro)
```

Cada archivo de `routes/` sigue el mismo patrón: Express Router, funciones `async`, y
respuestas JSON con la forma `{ success: true/false, data/error }`.

## Consideraciones para mantenimiento

- El pool de conexiones a PostgreSQL está limitado a 5 conexiones concurrentes — subirlo
  si el tráfico de demo lo justifica.
- No hay *rate limiting* en los endpoints públicos (`GET /api/pets`, `GET /api/lost-pets`)
  — agregar si se expone la demo públicamente por tiempo prolongado.
- Las columnas `marker_top`/`marker_left` de `lost_pets` guardan coordenadas reales bajo
  un nombre heredado — ver nota en 2.11 antes de tocar la lógica de mapas o alertas.
- El README.md que se había agregado el 11 de junio (commit `95104ba`) ya no existe en
  el repositorio — recrearlo con, como mínimo, esta sección de instalación.
- Cuando se integre el proveedor de IA (2.10), documentar acá el costo por uso y el
  límite de requests para no generar sorpresas de facturación.
